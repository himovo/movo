# Personal server file space

Server conversations use one persistent directory per tenant and user under the `sandbox-workspaces` volume. Each conversation has its own subdirectory. The directory is mounted at `/job/home` in isolated DSH runtimes and script containers; the DSH session working directory is `/job/home/conversations/<conversation-key>`.

The keys are opaque hashes of trusted tenant, user, and conversation IDs. Containers receive only the current user's volume subpath. Desktop sessions with a selected local workspace keep their existing workspace behavior.

Uploaded documents and images are copied into the conversation's `inputs` directory after ownership checks. `run_script` uses `/job/home/work` as its writable `work_dir` for intermediate files and dependencies across calls, turns, and conversations. Its `HOME` and `TMPDIR` also point into that persistent work directory. DSH plugin runtimes use `/job/home/tmp` for temporary files. Scripts can also access `home_dir` and `conversation_dir`. Files left in a script's per-call `output_dir` are copied into the conversation's `outputs` directory and exported through the existing artifact flow. Supported files written by DSH plugin tools in the conversation directory are published as conversation downloads. The `inputs` and `outputs` directories are excluded from the plugin output scan to prevent duplicate cards.

Internal script call directories are archived for audit and then removed at turn completion. The user's `work_dir` and conversation directories remain across turns and runtime restarts. They are removed only when the user or an operator explicitly removes the files; upgrading service images does not clear the volume. Back up `sandbox-workspaces` as part of deployment data, and restore it alongside the application's storage metadata.

`MOVO_PERSONAL_SPACE_MAX_BYTES` defaults to 2 GiB per user. Upload staging and script output copying check this limit before writing. Scripts and DSH plugin tools can write directly to the mounted directory, so this is an application-level limit, not a filesystem quota. Operators who need a strict limit must apply a quota to the backing filesystem. A full space does not prevent a script from running to inspect or delete files. Input staging is limited to 20 attachments and 256 MiB per turn; output delivery is limited to 50 supported files and 256 MiB per turn.
