# DSH 插件兼容升级方案

> 状态：实施中。阶段进展与尚未通过的验收见 `verification.md`；本文仍是最终验收口径，不能把能力发现当作实际任务通过。

## 目标与边界

MOVO 保留用户、组织、企业权限、管理后台和 Vue 对话界面；DSH 继续负责插件的安装、Host 生命周期和实际执行。一个 DSH 插件贡献的工具、Skill、命令、MCP 或 Client UI，按实际能力接入 MOVO，不把它们复制为独立的 MOVO Skill、工具或 MCP 安装记录。它们始终关联来源插件，并继承该插件的可见范围和执行权限。对话模型统一由 MOVO 模型中心配置；插件贡献的模型提供方仅作诊断展示，不进入 MOVO 模型选择器。

兼容性的判定以**当前用户的实际 DSH Runtime/Session 中可发现、可调用的能力**为准，不能仅凭 `package.json` 声明，也不能仅凭插件是否新增 `globalTools`。插件安装成功、Runtime 启动成功、Session 暴露能力、一次真实调用成功是不同状态，界面应如实区分。

本项目不修改 DSH 源码；通过 MOVO 自有适配层、API 和前端接入。所有新增前端文字提供中文、英文翻译，业务代码不写中文文案或注释；实现按职责拆分模块。

## 实施工作项

### 0. 固定 DSH 版本下的插件兼容预检

- 以**当前运行容器中的 DSH 版本**为准，并与 MOVO 锁定版本比较；若部署实际版本与锁定版本不同，先报部署异常，不用预期版本替代实测版本。当前代码固定 `0.2.1-alpha.1`，后续升级按实际锁定值更新。
- 安装前让 DSH 原生插件管理器 `inspect` 精确的插件版本，取得包信息；当前 DSH 的 `inspect` 结果不提供 peer 兼容结论，真正的版本拒绝发生在 `installBundle` 和 Profile 启动阶段。展示插件版本、运行中的 DSH 版本、检查结果和原始诊断。`package.json` 中的 peer 声明可作为解释信息，**最终判定以 DSH 原生安装和隔离 Runtime 启动结果为准**。预发布版本的范围匹配不自行用字符串或简化规则推断。
- 状态区分“兼容并已验证”“声明兼容但尚未运行验证”“版本不兼容”“缺少兼容声明/无法确定”“下载或依赖失败”。版本不兼容时不写入可启用插件记录，也不自动放宽 DSH 的精确版本豁免；无法确定时只允许继续隔离验证，通过前保持未验证状态。保留 DSH 的错误代码和诊断，给管理员可执行的处理建议。
- 允许管理员选择该插件**明确兼容**当前 DSH 的旧版或其他固定版本；不自动安装 `latest`，不因单个插件自动升级整个 DSH。若只有新版 DSH 才支持，记录为受 DSH 锁定版本阻断，交由 MOVO 正常的 DSH 升级流程评估兼容矩阵、会话恢复、镜像发布与回滚。
- MOVO/DSH 升级后重新核对已安装插件的版本兼容性和实际 Runtime 激活结果；不静默把被 DSH 跳过的插件当作可用。旧会话若仍引用不可用插件，应给出明确状态且保持会话其他能力可用。
- 离线包导出记录插件精确版本与来源端 DSH 版本；导入端先比对运行 DSH，再尝试 DSH 原生验证。版本或基础镜像不匹配时说明原因，不能仅因 ZIP 导入成功就显示兼容。

### 1. 建立插件能力清单与状态

- 从用户可用的 DSH Runtime 和 Session 读取实际能力，形成 MOVO 只读投影：插件 ID/版本、来源范围、能力类别、DSH 标识、用户可调用/模型可调用、所需环境、发现时间、验证状态。
- 覆盖 Agent 工具、Host 服务/事件、Skill、命令、MCP 服务器及工具、模型/能力提供、Client UI 和配置型 Bundle。某类能力若当前 DSH API 不能稳定枚举，应明确显示“未验证/暂不支持”，不可猜测为可用。
- 安装、启停、升级、Profile 变化、Runtime 重建后刷新投影；避免以安装时一次扫描结果永久代表当前状态。能力 ID 由“来源插件 + DSH 原生能力标识”构成稳定引用，不与 MOVO 原生资源 ID 混淆。
- 不将插件内置 Skill/MCP 写入 MOVO 原生 Skill/MCP 表，不为它们创建第二份生命周期或专属 Skill 镜像。

### 2. 接入各类执行入口

- **Agent 自动调用**：DSH 原生工具、模型可调用 Skill 和 MCP 工具保留在所属 Runtime/Session 中；MOVO 只投影允许 Agent 使用的能力，不另起一套执行器。
- **用户主动调用**：`/` 菜单统一展示 MOVO Skill、插件贡献且 `userInvocable` 的 Skill，以及 DSH 命令；标记来源插件。命令、Skill 同名时遵循 DSH 的实际解析优先级，并在界面避免含糊选择。选中后通过对应 DSH 协议/会话入口执行，不能把命令文本伪装成提示词。
- **MCP**：区分 MCP server 的配置/启动与其多个 tool 的可见性；stdio 进程在插件 Runtime 中启动，HTTP endpoint 按现有网络策略连接。只有会话已注册的工具才标为可用。
- **插件模型提供方**：只记录 DSH 实际发现的提供方名称，明确标为诊断信息；不请求插件的模型目录。MOVO 模型选择器、模型权限和实际对话继续使用模型中心；不为插件模型提供方新增配置或执行入口。插件仅提供模型时，不能把“运行时已加载”表述成“模型已可在 MOVO 使用”。
- **Host 服务/事件和配置 Bundle**：允许无对话工具的插件正常安装、启用、运行，并通过对应 Host 状态和行为验证；不强制要求有聊天工具。
- **Client UI**：优先复用 DSH 提供的 Client 模块或原生页面能力，MOVO 负责导航入口、当前用户身份、同一 Runtime/Session 上下文、权限和错误边界。先做最小真实插件的端到端验证，再确定嵌入方式；不要预设 React 组件能直接挂进 Vue。无可用浏览器模块的插件不显示空入口。

### 3. 执行环境、重建与离线迁移

- 继续使用共享 DSH 插件基础镜像与隔离 Runtime，不为插件内置 Skill 另建 MOVO Skill 镜像。插件需要的 npm/pnpm、APT、Python、浏览器等依赖，在插件 Runtime 或其构建流程中按实际插件要求准备；仅复用已验证且与镜像、架构、版本匹配的缓存。
- 明确基础镜像、插件包及传递依赖、插件 Profile、运行状态四层对象。升级时检查是否可以复用已准备环境；只有依赖或基础条件确实变化才重建。准备中、可复用、失败和不可用的状态需与真实队列/日志一致。
- 在线端离线导出至少覆盖**插件安装包及可再安装的依赖缓存**和**所需隔离基础镜像**；如果插件依赖额外系统包或运行时下载资源，应在导出前给出完整性检查与缺项。当前 ZIP 导入会校验 OS/架构，并对涉及的 Skill/插件包校验对应基础镜像 ID；迁往另一台机器时必须先导入匹配镜像，再导入包源。
- 在离线端按“镜像导入 → 包源导入 → 插件安装/启用 → Runtime 启动 → Session 能力发现 → 实际调用”验收。导入包源不能直接标记插件已安装或可用。禁用公网后重复同一流程，确认未发生隐式在线拉取。
- 管理后台沿用现有“系统状态 / 隔离沙箱镜像”和“离线包源 / 环境准备记录”的入口，补充插件来源、基础镜像 ID、准备记录、缺失依赖和可导出性关联；不要增加平行的插件镜像页面。

### 4. 企业权限与安全边界

- AskAI 复用 `plugin.runtime` 总开关及范围、组织插件的现有授权范围；社区版保持现有产品扩展行为。插件贡献的 Skill、MCP 工具、命令和 UI 继承父插件权限，不新增独立授权项。插件模型不作为 MOVO 对话入口。
- 每个入口做到双重约束：仅向授权用户展示，且服务端执行前再次校验。关闭总开关、撤销插件授权、禁用插件后，已有会话刷新/继续执行时也不能绕过；Agent 自动发现、直接 API 请求和旧会话恢复同样受控。
- 个人插件与组织插件同名、授权变化及运行中会话的处理遵循现有 Profile/资源策略；如实际 DSH Runtime 无法即时撤销能力，先阻断 MOVO 入口并让后续 Session 重建生效，明确状态与时点。
- 插件 UI/API 不能只依赖前端隐藏；身份令牌、租户、插件归属和 Session/Runtime 绑定要在服务端校验。保持现有容器隔离、网络出口和资源配额。

## 分阶段交付与验收

| 阶段 | 可交付结果 | 最低验收 |
| --- | --- | --- |
| 0. 版本预检 | 安装前展示运行 DSH、插件精确版本、兼容结果及诊断；升级后复检。 | 兼容版本可进入 Runtime 验证；不兼容版本不能启用，报错明确；旧会话可继续使用其余能力。 |
| A. 能力发现 | 分类能力清单、状态和来源关联；修正只看 `globalTools` 的安装判定。 | 纯工具、纯 Host、纯 UI、包含多个 Skill/MCP 能力的插件不会被错误归类；安装失败与未验证可区分。 |
| B. 对话入口 | Agent 可调用能力、`/` Skill/命令和 MCP 多工具按实际能力接入；模型选择仍由 MOVO 模型中心负责。 | 选中一个插件 Skill/命令后调用正确 DSH 入口；未授权能力不进入 Agent 或用户菜单；插件模型不出现在模型选择器。 |
| C. Client UI | 一个真实 Host+Client 插件通过当前用户身份和同一 Runtime/Session 使用。 | 页面可打开、操作可执行、权限撤销后拒绝访问，Vue 页面未被迫重写为 React。 |
| D. 环境与离线 | 环境复用、准备日志、完整性校验以及镜像和包源迁移闭环。 | 在线准备后导出；另一台同架构内网主机先导入镜像和包源，断网安装同版插件并完成真实调用。 |
| E. 企业版 | 将各入口接到既有 AskAI 两层插件权限。 | 全员/指定范围/禁用三种状态覆盖列表、Agent、命令、UI、直接 API 和旧会话。 |
| F. 真实 Skill 验收 | 下载公开发布、可追溯版本的真实 Skill，并运行其原有任务。 | 独立 Skill 和插件内置 Skill 均完成安装、环境准备、对话选择或 Agent 调用、脚本/工具执行及产物核对；离线端复跑依赖型用例。 |

联调插件至少覆盖：仅提供 Agent 工具、Host 事件但无工具、多个用户可调用 Skill/命令、多个 MCP 工具、Host+Client UI、需系统/语言依赖的插件。每类必须在 MOVO 普通会话和真实隔离 Runtime 中验证，不能只通过包检查。若测试插件还提供模型，应确认其模型只在能力诊断中出现，不进入 MOVO 模型选择器。桌面端本地工作区行为单独回归，避免服务端改动影响桌面端。

以下四个真实插件为**必测对象**，不能用自制插件或只运行单元测试替代。实施时先锁定各自的官方安装来源和版本，逐个检查与当前 DSH 的兼容性和实际贡献的能力，再按检查结果执行至少一个真实用户任务；不预先假定某个版本必然提供指定入口。如果某插件没有兼容当前 DSH 的版本，必须留下 DSH 原生诊断并标为版本阻断，不能伪造通过结果或私自放宽版本约束。

| 必测插件 | 至少验证的用户任务与接入边界 |
| --- | --- |
| `dsh-media-desk` | 安装并启动隔离 Runtime；打开其实际提供的 Client UI，完成一个媒体处理任务，核对 Host 调用、文件产物和会话关联。 |
| `dsh-guizang-design` | 安装并发现其实际贡献的 Skill/工具/界面；从普通会话选择或调用一个设计任务，核对依赖准备、执行结果和插件来源标记。 |
| `dsh-context` | 在真实会话中触发上下文洞察能力，验证 Host/事件或 Client UI 的实际入口，以及同一用户、同一会话的结果与权限边界。 |
| `agentero-dsh` | 安装后执行一次论文导入或阅读任务，验证文件/外部资源、隔离环境、实际工具调用和可查看的结果。 |

每个插件均需留下安装包来源与固定版本、DSH 能力清单、环境准备记录、Session/Runtime 标识、操作步骤、结果截图或产物、错误日志；在 AskAI 再验证授权和未授权用户的可见性与直接调用结果。若插件需要账户、密钥或外部服务，应记录条件并准备可公开复现的测试数据；受这些条件阻断的项目标为“未通过验收”，不能算通过。至少选择其中一个有外部依赖的插件，走完整的镜像与离线包源导出、异机断公网导入、重新安装和真实调用流程。

最终真实 Skill 测试不得只使用自制探针：从公开仓库下载有明确来源、版本和许可的 Skill 包，至少选一个声明 Python/npm/APT 依赖并实际调用脚本的独立 Skill，以及一个由真实 DSH 插件贡献、允许用户主动选择的 Skill。记录下载地址、固定 commit/版本、依赖清单、准备记录、实际执行命令或对话、输出文件及核对结果。对依赖型独立 Skill，在在线端准备并导出所需包源和镜像，在另一台同架构且断公网的环境导入后重新安装、执行；对插件内置 Skill，验证它复用所属插件 Runtime、继承插件权限，且不触发 MOVO 独立 Skill 镜像构建。若某个真实包需要外部密钥或服务，换用可复现的公开包，不能以“安装成功”替代实际执行验收。

## 开工前需固定的接口决定

1. DSH 当前版本对 Skill、命令、MCP、Client 模块、模型的可枚举 API 与会话调用协议：逐项做源码/API 证据表，再定适配接口；不把猜测写成实现承诺。
2. 插件能力变更后已存在会话的刷新策略，以及权限撤销的最迟生效点。
3. 离线包“完整”的边界：安装时依赖缓存之外，运行时下载资源是否可捕获；无法捕获时显示缺项和可复现的安装要求。

完成上述接口核对后，再按 0 → A → F 分批实现和验收。每阶段分别提交可审查的模块与测试；不在单个大文件堆积兼容逻辑。
