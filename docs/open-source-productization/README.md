# MOVO Open Source Productization Strategy

本文档沉淀 MOVO 开源产品化方向的核心判断。重点不是把现有能力包装成通用工作流平台，而是围绕企业真实任务现场，明确 MOVO 与 Dify 类产品的差异、用户使用路径、部署形态和后续工程拆分节奏。

## 1. 核心定位

MOVO 应定位为：

> 面向企业真实业务现场的目标驱动智能体平台。终端用户只描述目标，管理员通过对话、文档和操作示范教会系统，AI 自动编排并执行任务。

这个定位和传统低代码工作流平台不同。传统平台强调用户手工设计 workflow：选择节点、连接分支、配置工具、填写 API 参数、处理失败路径。MOVO 的产品立场应该是：

> 不要求人从零设计工作流，而是由 AI 根据目标自动生成执行计划，人类只审阅关键决策、约束策略和批准风险动作。

更准确的表达是：

> AI 自动编排，过程可解释，风险可审批，结果可验收，路径可沉淀。

## 2. 与 Dify 的差异判断

Dify 的强项是 LLM 应用开发平台：可视化 workflow、Prompt IDE、RAG pipeline、模型管理、工具接入、应用发布和 LLMOps。它适合技术人员或实施人员构建 AI 应用。

MOVO 不应该直接复制这条路线。MOVO 的差异应集中在以下方向：

1. 目标驱动自动编排
   用户描述业务目标，系统自动生成任务图、选择技能和工具、插入审批点，并展示可解释执行计划。

2. 复杂交付物生产线
   内容生成不是简单文本输出，而是围绕报告、文章、PPT、DOCX、XLSX、表单填写、多轮修订和导出完整交付物建立流水线。

3. 浏览器自动化执行
   在企业系统 API 不完善的情况下，通过浏览器观察、点击、填写、上传、下载、截图、人工接管和轨迹学习完成业务系统操作。

4. 管理员低门槛训练智能体
   管理员不需要手工画复杂 workflow，而是用对话、SOP 文档、模板文件、历史样例和浏览器示范生成可复用智能体能力。

5. 执行可靠性
   任务图、checkpoint、resume、idempotency receipt、审批、审计、失败恢复和执行回放应该成为核心能力，而不是隐藏实现细节。

一句话区分：

> Dify 让人设计自动化；MOVO 让 AI 设计自动化，并负责把任务执行到可验收结果。

## 3. 用户角色

企业智能体平台不应只分“终端用户”和“管理员”。更合理的是三类角色。

### 3.1 终端用户

终端用户只使用一个对话入口完成任务。

示例：

- 帮我根据这个 Excel 生成经营分析报告，并导出 Word。
- 登录 CRM，查询客户 A 最近三个月跟进记录，整理成拜访纪要。
- 把这份合同翻译成英文，保持原格式。
- 根据这些资料做一份 10 页 PPT。
- 帮我给客户 A 提交报价审批，提交前让我确认。

终端用户看到的是任务进度、证据、待确认事项和最终交付物，而不是 workflow 节点画布。

### 3.2 业务管理员 / 运营管理员

业务管理员懂业务流程，但不一定懂 API、插件、参数、分支和异常处理。他们的核心任务不是配置节点，而是教会系统怎么做事。

他们应该通过以下方式训练能力：

- 对话式配置智能体
- 上传 SOP、制度文档、模板、历史优秀样例
- 在浏览器中操作示范一遍业务流程
- 审阅 AI 生成的任务计划、输入字段、输出模板和验收标准
- 发布能力给指定部门或用户组

### 3.3 技术管理员 / 平台管理员

技术管理员负责平台底座：

- 模型供应商配置
- SSO、组织、角色、权限
- 数据库、对象存储、知识库
- API connector 和内部系统接入
- 浏览器沙箱和本地桌面桥
- 审批策略、审计日志、成本和监控
- 私有化部署和运维

## 4. 推荐产品入口

### 4.1 终端用户入口

终端用户入口应是对话框 + 执行视图：

- 目标理解
- 自动计划
- 当前执行步骤
- 工具调用证据
- 浏览器截图或操作记录
- 风险确认
- 文件交付
- 多轮修订

不应把 workflow 画布作为默认入口。

### 4.2 管理后台入口

管理后台不应叫“工作流配置中心”，而应围绕能力训练组织。

可选命名：

- 能力训练
- 业务技能中心
- 智能体教练台
- 流程学习
- 操作示范
- 任务策略管理

管理后台核心模块：

- 智能体能力库
- SOP / 模板 / 样例导入
- 浏览器操作录制
- 工具和连接器管理
- 站点画像与登录态管理
- 发布范围和权限管理
- 审批策略
- 执行日志与审计
- 质量评估和回归测试

## 5. 无 API 企业系统的机会

许多企业内部系统并没有完善 API：

- 老系统没有开放接口
- API 文档无人维护
- 权限复杂
- 数据只能从网页读取
- 流程依赖人工操作
- 表单字段经常变化
- 业务规则藏在人的经验里

这不是障碍，而是 MOVO 的机会。浏览器自动化、录制生成技能、页面理解、人工接管和轨迹学习可以让 MOVO 覆盖 Dify 类 API-first 平台不擅长的场景。

推荐能力闭环：

1. 管理员在业务系统中操作一遍。
2. 系统记录页面、元素、输入、点击、上传、下载和结果。
3. AI 抽象变量、步骤、前置条件、风险动作和失败兜底。
4. 管理员确认后发布为技能。
5. 终端用户通过自然语言调用。
6. 执行中遇到不确定点可人工接管。
7. 人工纠偏沉淀为后续策略。

## 6. 开源仓库组织建议

第一阶段建议采用 monorepo，不建议过早拆成多个 Git 仓库。原因：

- 前后端、桌面端、runtime、browser、skills 仍在强耦合演进期。
- 多仓库会增加版本匹配和部署文档复杂度。
- 开源用户更关心一条命令能不能跑起来。

推荐目录形态：

```text
movo/
  backend/                  # 现有后端，后续可命名为 runtime-api
  frontend/                 # Web 端，第一阶段可同时承载用户端和管理端
  desktop/                  # 桌面端 / 本地浏览器桥
  docs/
  deploy/
    docker-compose/
    helm/
  examples/
  packages/
    sdk-js/
    sdk-python/
    shared-types/
    skill-spec/
```

更成熟后的目标形态：

```text
movo/
  apps/
    web/                    # 用户端 + 管理端 Web
    desktop/
  services/
    runtime-api/
    worker/
    sandbox-gateway/
  packages/
    sdk-js/
    sdk-python/
    shared-types/
    skill-spec/
  deploy/
  docs/
  examples/
```

注意：产品上可以区分用户端和管理端，但工程上第一阶段不必拆成两个 Web 容器或两个 API 服务。

## 7. Docker 部署形态

开源用户最需要的是：

```bash
git clone https://github.com/your-org/movo.git
cd movo
cp .env.example .env
docker compose up -d
```

用户访问一个入口即可完成初始化。

### 7.1 最小可用版

```text
nginx
web
api
mongo
local-storage volume
```

说明：

- `web` 承载用户端和管理端前端。
- `api` 承载对话、任务运行时、管理 API。
- `mongo` 本地化数据库。
- 文件先落本地 volume，降低开源启动成本。
- `nginx` 统一入口和反向代理。

### 7.2 推荐开源版

```text
nginx
web
api
worker
mongo
redis
local-storage volume
```

说明：

- `worker` 处理长任务、文件解析、渲染、浏览器任务、重试等异步执行。
- `redis` 作为队列和缓存。
- `api` 专注请求入口、鉴权、流式事件、状态查询。

### 7.3 增强版 / 企业部署

```text
nginx
web
api
worker
mongo
redis
minio
browser-sandbox
vector-db
observability
```

说明：

- `minio` 作为 S3 兼容对象存储，替代云 OSS。
- `browser-sandbox` 支持远程浏览器执行。
- `vector-db` 用于企业知识库。
- `observability` 可包含 Prometheus、Grafana、OpenTelemetry collector 等。

## 8. 是否需要 MinIO

MongoDB 必须本地化，否则会话、任务状态、执行日志、技能和文档记录都无法独立运行。

对象存储建议支持两档：

1. 默认 `local-storage`
   - 最低启动成本。
   - 类似 Dify 默认挂载本地 storage volume。
   - 适合开源体验和开发环境。

2. 可选 `s3/minio`
   - 更接近生产对象存储。
   - 适合企业内网部署。
   - 后续可兼容 S3、MinIO、阿里云 OSS、腾讯云 COS、华为 OBS 等。

推荐环境变量：

```env
STORAGE_BACKEND=local
LOCAL_STORAGE_PATH=/app/storage
FILE_PUBLIC_PATH_PREFIX=/askai-api/api/files
BACKEND_INTERNAL_BASE_URL=http://backend:8000
```

本地模式下后端实际文件路由是 `/api/files/{object_path}`。如果前端统一通过
`/askai-api` 访问后端，需要网关或开发代理继续把 `/askai-api/api/*` 转发到
后端 `/api/*`，这样 MOVO 前端和 gr_wechat_dialog 的现有调用路径都不需要改。

可选：

```env
STORAGE_BACKEND=oss
OSS_ACCESS_KEY_ID=...
OSS_ACCESS_KEY_SECRET=...
OSS_BUCKET_NAME=askagentic
OSS_ENDPOINT=https://oss-cn-beijing.aliyuncs.com
OSS_REGION=cn-beijing
```

## 9. 参考 Dify 的工程实践

Dify 的工程组织对 MOVO 有参考价值：

- 使用 monorepo，而不是前后端分仓库。
- 根目录包含 `api/`、`web/`、`docker/`、`packages/`、`sdks/`、`docs/`。
- 通过 `docker compose up -d` 一条命令启动。
- 一个 Web 容器承载前端。
- 一个 API 镜像通过 `MODE=api`、`MODE=worker`、`MODE=beat` 区分进程角色。
- 使用 nginx 统一代理 Web 和 API。
- 依赖服务本地化，包括数据库、Redis、sandbox、plugin daemon 等。
- 可选能力通过 compose profiles 启用，如向量数据库和证书服务。

MOVO 可以学习这些工程策略，但不应复制 Dify 的产品定位。MOVO 应把重点放在：

- AI 自动编排任务图
- 交付物生成流水线
- 浏览器自动化执行
- 管理员低门槛训练智能体
- 企业系统无 API 场景落地

## 10. 开源前最低门槛

开源前至少完成：

1. 脱敏和密钥轮换
   当前开发环境中的真实密钥、数据库连接串和云服务 token 不能进入开源历史。

2. `.env.example`
   提供可本地启动的默认配置，不依赖内部测试环境。

3. 本地 MongoDB
   docker compose 内置 MongoDB，并自动初始化索引。

4. 本地文件存储
   默认支持 local volume；可选 MinIO/S3。

5. 一键启动
   `docker compose up -d` 后可访问 Web 初始化页面。

6. 初始化向导
   创建管理员账号、配置模型供应商、选择存储方式、启用或跳过浏览器能力。

7. 示例任务
   至少提供报告生成、Office 文件导出、浏览器录制/回放三个示例。

8. 开源治理文件
   `LICENSE`、`CONTRIBUTING.md`、`SECURITY.md`、`CODE_OF_CONDUCT.md`、发布说明。

## 11. 分阶段路线

### 阶段一：开源可运行

- monorepo
- 一个 Web
- 一个 API
- MongoDB 本地化
- local storage
- docker compose 一键启动
- 基础示例任务

### 阶段二：执行可靠性

- worker 独立
- Redis 队列
- 任务状态可视化
- checkpoint/resume 产品化
- 审批 UI
- 执行日志回放

### 阶段三：管理员训练能力

- 对话式智能体配置
- SOP / 模板导入
- 浏览器录制生成技能
- 技能发布和权限范围
- 质量评估和回归测试

### 阶段四：企业部署

- SSO/RBAC
- 审计日志
- 多租户隔离
- MinIO/S3
- Helm chart
- 监控和成本分析
- 浏览器 sandbox gateway
- 知识库和向量数据库可选部署

## 12. 关键结论

MOVO 不应只是另一个工作流平台。它应该把复杂性从用户侧拿回来：

- 终端用户只提目标。
- 管理员用对话、文档和示范训练能力。
- AI 自动编排任务图。
- 平台负责执行、恢复、审批、审计和交付。

第一阶段工程上不必拆太细。推荐：

```text
web + api + mongo + local-storage + nginx
```

随后逐步增加：

```text
worker + redis + minio + browser-sandbox + vector-db
```

这样既能保证开源用户马上跑起来，也为后续企业级部署保留清晰扩展路径。

## 13. 当前分支的产品化原则

如果当前分支已经和另一套系统完成集成并投入使用，不建议长期维护“集成版分支”和“开源版分支”两条产品线。长期双分支会持续带来功能双写、修复不同步、接口漂移和发布复杂度上升的问题。

更合适的策略是：

- 保持一个主干持续演进
- 把与外部系统耦合的部分收敛为明确的集成适配层
- 通过配置、部署形态和能力开关区分开源默认模式与集成模式

一句话总结：

> 不做长期双分支，而是采用单主干 + 私有集成层 + 开源默认配置。

这意味着开源化工作的重点不是复制出另一套仓库逻辑，而是逐步把当前项目整理成：

- 一套通用主干能力
- 一套可插拔的企业集成能力
- 一套开箱即用的开源默认部署方案

## 14. 近期优先级判断

如果目标是让开源用户快速上手，同时又为企业内部推广做准备，那么优先级应当明确收敛，避免一开始就扩展成完整企业平台。

第一优先级应是降低启动门槛：

1. MongoDB 本地化
2. 远程 OSS 改为默认本地文件存储
3. 提供最小初始化流程
4. 保证一键启动后即可进入系统试用

原因很直接：如果开源用户第一次体验就必须准备云存储、外部数据库和复杂配置，产品几乎无法形成有效扩散。

因此开源第一阶段的核心目标不是“功能最全”，而是：

> 让用户用尽可能低的准备成本，把系统跑起来并完成第一次有效任务。

## 15. 开源版产品路线建议

### 15.1 阶段一：开源可运行

这一阶段面向开源体验，目标是让个人开发者或企业测试人员在较短时间内完成部署和试用。

核心范围建议控制在：

- 本地 MongoDB
- 本地文件存储
- 默认模型配置入口
- 单一可访问入口
- 基础初始化流程

初始化流程建议只解决最基本问题：

- 创建管理员账号
- 配置至少一个模型供应商
- 选择默认存储方式
- 启用或暂时跳过浏览器相关能力

这一阶段不要先追求复杂组织体系，也不要先做庞大的企业后台。

### 15.2 阶段二：管理后台骨架

当系统已经具备低门槛启动能力之后，再进入管理后台建设。管理后台的第一版不应做成繁杂的配置中心，而应聚焦最关键的运营闭环。

建议优先建设五类核心模块：

- 系统初始化与管理员管理
- 模型配置管理
- 工具 / 连接器管理
- 技能管理
- 用户与权限管理

这五类模块分别回答五个问题：

- 谁能进入系统并拥有管理权限
- 系统可以调用哪些模型
- 系统可以连接哪些企业工具和业务系统
- 系统具备哪些可发布的能力
- 哪些用户或部门可以使用哪些能力

### 15.3 阶段三：企业内推广运行

当后台骨架可用后，下一阶段重点不是继续堆叠配置项，而是建立企业内部可推广、可管控、可审计的运行机制。

建议优先补齐：

- 管理员注册与登录
- 组织内用户登录
- 模型配置与可用范围控制
- 工具 / 连接器接入与授权管理
- 技能发布与范围控制
- 审计日志与基础运营视图

目标是形成完整闭环：

- 管理员能配置
- 普通用户能使用
- 权限边界可控
- 使用过程可追踪
- 能按部门逐步推广

### 15.4 阶段四：企业身份体系整合

钉钉、飞书、企业微信等能力很重要，但不建议一开始并行深做三套逻辑。更合理的方式是先抽象统一的企业身份接入层，再分别接入不同平台。

建议顺序：

1. 先有本地账号体系
2. 再抽象统一身份接入模型
3. 最后接入钉钉、飞书、企业微信

后台管理系统应聚焦统一问题：

- 用户从哪里来
- 组织架构从哪里来
- 登录态如何接入
- 角色和部门如何映射

这样可以避免系统在早期被不同平台的细节牵着走。

### 15.5 阶段五：低门槛能力训练

在企业基础能力稳定后，再重点建设“管理员如何低门槛训练系统”这一层。

建议逐步建设：

- SOP 文档导入
- 模板与历史样例导入
- 浏览器操作示范与录制
- 文档生成 skill 管理
- 技能发布、评估与回归测试

这一阶段的目标不是增加更多配置页面，而是让管理员真的能把业务经验沉淀为可复用能力。

## 16. 后台管理系统的产品分层

后台不应只是技术设置中心，而应围绕平台运行和能力运营建立清晰分层。

建议拆成三层：

### 16.1 平台设置层

负责平台底座的可运行能力，包括：

- 管理员与系统初始化
- 模型配置
- 存储配置
- 登录方式与基础系统参数

### 16.2 能力运营层

负责把系统能力组织、发布和维护起来，包括：

- 工具与连接器管理
- skills 管理
- 模板、样例和文档生成能力管理
- 发布范围与可见范围控制
- 基础质量评估与运营视图

### 16.3 组织推广层

负责在企业内部可控扩展，包括：

- 用户、部门、角色管理
- 权限范围管理
- 企业身份体系整合
- 审计与推广运营

这种分层方式有助于避免后台被做成杂乱的“配置页面堆积”，也更符合 MOVO 后续面向企业落地的产品方向。
