# 图规划能力端到端测试用例 (Graph Planning E2E Test Cases)

本文件整理了一系列针对 AskAI 多智能体系统**图规划（Graph Planning）**能力的端到端测试用例。这些用例基于当前系统已注册的 Mock 接口（门店巡检、经营诊断、销售复盘），涵盖了单工具调用、多工具顺序调用、循环节点（Loop/Map）、条件判断节点等各种复杂编排场景。

你可以直接在前端 Chat 窗口中输入对应的 **测试 Prompt**，观察后端控制台日志与前端时间线的变化，验证系统是否能够按照预期规划出正确的图结构并完成任务。

---

## 1. 基础场景（单接口与顺序链条）

### 用例 1.1：单接口调用 (Single Tool Call)
*   **测试目的**：验证最基础的图规划能力，系统只需识别并调用一个工具即可完成任务。
*   **测试 Prompt**：
    > “请帮我获取华东直营门店当前的巡检工单列表，并告诉我一共有哪些门店。”
*   **预期图规划**：
    1.  **节点 1 (Tool Call)**：调用 `get_store_audit_tasks`（门店巡检工单列表查询）接口。
    2.  **节点 2 (Response Generation)**：提取返回的门店名称列表并直接输出。
*   **特点**：无分支、无循环、单节点。
*   **前端验证点**：
    1.  时间线显示工具调用与任务完成。
    2.  聊天正文必须出现可读 Markdown 回复，而不是只显示时间线。
    3.  正文必须包含门店名称列表与门店总数。
    4.  正文不应是完整原始 JSON。
    5.  正文只出现一次，不应重复输出两段 answer。

### 用例 1.2：双接口顺序链条调用 (Sequential Tool Chain)
*   **测试目的**：验证两个接口的前后依赖关系。系统需要将前一个接口的输出作为后一个接口的输入。
*   **测试 Prompt (显式步骤版)**：
    > “请帮我查询当前的巡检工单列表。找到上海徐汇店的工单ID后，再用这个工单ID去查询其巡检详情，并以表格形式整理该店各模块的得分和整改状态反馈给我。”
*   **测试 Prompt (语义规划版 - 推荐)**：
    > “请帮我查一下上海徐汇店最近的巡检打分详情，并以表格形式汇总各模块的得分和整改状态。”
*   **预期图规划**：
    1.  **节点 1 (Tool Call)**：调用 `get_store_audit_tasks` 获取工单列表。
    2.  **节点 2 (Data Extract)**：从列表中提取出上海徐汇店的 `task_id`（如 `current-audit-sh-xuhui`）。
    3.  **节点 3 (Tool Call)**：调用 `get_store_audit_task_detail` 传入获取的 `task_id` 获取巡检详情。
    4.  **节点 4 (Response Generation)**：将返回的各项指标得分与整改反馈渲染成 Markdown 表格输出。
*   **特点**：顺序链条依赖，无条件分支，无循环。

### 用例 1.3：三接口顺序链条调用 (Three-Tool Sequential Chain)
*   **测试目的**：验证多于两个接口的长链条顺序依赖关系，确认图规划器可以在不借助循环或条件节点的情况下，顺畅地完成 3 步式数据流转。
*   **测试 Prompt (显式步骤版)**：
    > “第一步，请调用经营诊断快照接口，找出当前库存缺货 SKU 数量（stockout_sku_count）最多的门店名称；
    > 第二步，调用巡检任务列表接口，查找该门店对应的巡检工单 ID；
    > 第三步，调用巡检工单详情接口，查询该工单 ID 的详细数据，并重点输出该店的库存（inventory）与人员配备（staffing）模块的具体扣分项与排查发现。”
*   **测试 Prompt (语义规划版 - 推荐)**：
    > “帮我找出目前缺货 SKU 最严重的门店，然后帮我查一下这家门店最新的巡检工单详细情况，把库存和人员配置的扣分和排查问题提取出来汇报给我。”
*   **预期图规划**：
    1.  **节点 1 (Tool Call)**：调用 `get_store_diagnosis_snapshot` 获取经营快照。
    2.  **节点 2 (Data Extract)**：分析得出库存缺货最多的是 `南京新街口店` (缺货 17 项)。
    3.  **节点 3 (Tool Call)**：调用 `get_store_audit_tasks`，从中提取 `南京新街口店` 对应的巡检工单 ID (`current-audit-nj-xinjiekou`)。
    4.  **节点 4 (Tool Call)**：调用 `get_store_audit_task_detail` 传入该工单 ID 获取详情。
    5.  **节点 5 (Response Generation)**：针对库存与人员配备提取扣分项与排查发现并回复给用户。
*   **特点**：三步顺序工具链依赖（Tool A -> Data Extract -> Tool B -> Data Extract -> Tool C），无条件判断，无循环。

## 2. 高级编排场景（循环与条件）

### 用例 2.1：工具调用 + 循环遍历节点 (Loop / Map Node)
*   **测试目的**：验证系统能否根据前序接口返回的列表，**动态分裂并并行/串行执行多个子任务节点**（Map 机制）。
*   **测试 Prompt (显式步骤版)**：
    > “请帮我查询当前周期（2026-06）华东直营门店的所有巡检工单列表。获取列表后，请遍历并查询每一个工单的详情（task-detail），统计出哪些门店存在 critical（严重风险）的项目，并输出一份风险门店汇总报告。”
*   **测试 Prompt (业务视角版 - 推荐)**：
    > “帮我排查一下本月华东直营门店的所有巡检记录，找出哪些店存在严重隐患或违规项目？给我一份详细的整改排查汇总报告。”
*   **预期图规划**：
    1.  **节点 1 (Tool Call)**：调用 `get_store_audit_tasks` 获取所有巡检任务。
    2.  **节点 2 (Loop/Map)**：针对返回的工单（徐汇、浦东、西湖、新街口、苏州），循环调用 `get_store_audit_task_detail` 获取详情。
    3.  **节点 3 (Data Filter)**：过滤并分析哪些门店在 `sanitation`、`display`、`inventory` 等模块中含有 `status: "critical"`。
    4.  **节点 4 (Document Generation)**：汇总整改负责人、超期问题等，生成完整的 Markdown 风险汇总报告。
*   **特点**：触发图引擎的 Map/Loop 节点分裂执行。

### 用例 2.2：条件判断/分支选择节点 (Conditional / Branching Node)
*   **测试目的**：验证系统能否基于前序节点返回的动态数值指标，动态决定走向哪个执行分支。
*   **测试 Prompt (显式步骤版)**：
    > “获取 2026-06 华东直营门店的经营数据快照。如果上海浦东店的销售达成率（completion_rate）低于 70%，请拉取该门店对应的巡检工单详情（taskId 为 2026-06-audit-sh-pudong），核对卫生、库存、设备等各项指标是否正常，分析导致销售未达标的可能原因；如果达成率高于 70%，则只做常规经营分析，不用查询工单详情。”
*   **测试 Prompt (业务视角版 - 推荐)**：
    > “看一下我们华东各门店这个月的运营业绩。如果上海浦东店的业绩达成情况很不理想（低于七成），就去调出他们本月的现场巡检工单，看看是不是卫生、缺货或者设备出了什么严重问题，帮我分析下业绩差的根源；如果达成情况还可以，就只做一下浦东店的常规经营分析汇报。”
*   **预期图规划**：
    1.  **节点 1 (Tool Call)**：调用 `get_store_diagnosis_snapshot` 接口。
    2.  **节点 2 (Conditional)**：读取浦东店的 `completion_rate`（实际值为 `0.68`，低于 `0.70`）。
    3.  **分支节点 3 (True Branch - Tool Call)**：因为条件成立，进入真分支，调用 `get_store_audit_task_detail`，入参为 `2026-06-audit-sh-pudong`。
    4.  **节点 4 (Cross Analysis)**：结合经营异常数据和巡检中的 critical 项（如缺货 11 项、冷柜波动等），做根因交叉分析并生成报告。
*   **特点**：动态条件评估（If-Else 结构分流）。

## 3. 综合级编排场景（混合链路 + 复杂生成）

### 用例 3.1：混合节点 + 复杂格式导出 (Complex Mixed Pipeline)
*   **测试目的**：测试多节点链条、逻辑分支、循环过滤以及最后触发文档生成与导出下载的完整闭环。
*   **测试 Prompt (显式步骤版)**：
    > “获取最新的销售目标复盘快照。请检查总体的销售完成率（completion_rate）是否落后于时间进度（elapsed_rate）。如果已经落后，请找出所有销售完成率低于 60% 的销售代表（reps）以及存在 high 风险的关键商机（opportunities），并为他们生成一份目标改进建议文档，导出为 Word (DOCX) 格式。”
*   **测试 Prompt (业务视角版 - 推荐)**：
    > “帮我复盘一下销售团队目前的最新战报。看看我们目前的销售总额有没有落后于时间进度。如果进度滞后了，帮我把业绩不到六成的销售同事，以及当前有严重流失或延期风险的大单找出来，针对这些人和单子整理一份书面的销售改进与攻坚建议书，打包成 Word 文档导出来给我。”
*   **预期图规划**：
    1.  **节点 1 (Tool Call)**：调用 `get_sales_review_snapshot` 获取销售复盘快照数据。
    2.  **节点 2 (Conditional)**：对比 `completion_rate`（`0.6792`）与 `elapsed_rate`（`0.8065`），触发“落后”分支。
    3.  **节点 3 (Data Filter)**：过滤销售代表列表（如顾宁，达成率仅 `36.92%`）和 high 风险商机（如星河零售，跨月且预算审批受阻）。
    4.  **节点 4 (Doc Generation)**：编排生成改进建议文档。
    5.  **节点 5 (Docx Render)**：系统底层路由到 `docx` 渲染技能，生成真实 DOCX 并渲染供前端下载。
*   **特点**：条件分支 + 循环过滤数据 + 底层渲染转换（Word 导出）。

## 4. 企业级业务场景联合测试（多节点组合）

本节用例立足于企业真实业务流程，将**材料、抽取、统计、采集、内搜、外搜、工具、生成、翻译、填表、导出**等 backend 图规划节点组合起来，进行全链路测试。

### 用例 4.1：竞品动态分析与报告生成导出 (Competitor Intelligence Analysis)
*   **涉及节点**：`外搜` $\rightarrow$ `材料/抽取` $\rightarrow$ `翻译` $\rightarrow$ `生成` $\rightarrow$ `导出`
*   **业务场景**：市场研究部需要分析海外某竞品的最新动态，翻译其核心技术参数，并与本地产品手册对比，生成中文分析报告并导出 Word。
*   **测试 Prompt (显式步骤版)**：
    > “使用外部网络搜索查询最近竞品 AskAI-Pro 的英文版发布会核心功能与主要亮点。请抽取其中的关键特性翻译成中文，并结合我上传的我们自己的产品手册（附件材料），对比两者的优劣势，生成一份‘竞品对比分析报告’，最后导出为 Word 文档给我。”
*   **测试 Prompt (业务视角版 - 推荐)**：
    > “我们最近在华东市场遇到了竞品 AskAI-Pro 的激烈竞争。请上网搜一下他们最近英文发布会公布的最新功能亮点和技术参数，翻译并整理出来；然后结合我上传的我们自家的产品手册，客观对比分析我们的优劣势，为市场部出一份‘竞品防守与话术对比分析报告’，输出成 Word 格式。”
*   **预期图规划**：
    1.  **外搜节点**：调用搜索引擎检索关于 "AskAI-Pro launch features" 的最新英文信息。
    2.  **抽取与翻译节点**：从搜索结果中抽取主要特性，并将其翻译成中文。
    3.  **材料节点**：读取用户上传的产品手册附件。
    4.  **生成节点**：结合翻译后的竞品特性和手册内容，规划大纲并生成对比报告草稿。
    5.  **导出节点**：调用 `docx` 渲染模块生成 Word 文件。

### 用例 4.2：财务多门店异常诊断与表格回填导出 (Store Operational Audit & Ledger Export)
*   **涉及节点**：`工具` $\rightarrow$ `统计` $\rightarrow$ `内搜` $\rightarrow$ `填表` $\rightarrow$ `导出`
*   **业务场景**：财务与运营部定期审查门店。调接口获取数据，使用代码进行阈值统计，在内部知识库查找整改要求，将结果填入异常表格模版并导出 Excel。
*   **测试 Prompt (显式步骤版)**：
    > “请获取当前周期（2026-06）所有门店的经营数据快照。统计出销售达成率低于 80% 且客流量月环比出现下滑的门店。针对这些异常门店，去内部知识库搜索‘总部整改行动建议准则’，并将门店基本信息及对应整改意见自动填写进异常台账表中，最后以 Excel 表格格式导出给我。”
*   **测试 Prompt (业务视角版 - 推荐)**：
    > “帮我筛查一下本月经营状况滑坡的门店（达成率不足八成且客流环比下跌）。针对这些预警门店，对照我们总部的整改手册，给每个店匹配出相应的治理建议，把门店信息和整改策略汇总填到异常台账里，最后导出 Excel 发给我。”
*   **预期图规划**：
    1.  **工具节点**：调用经营快照接口 `get_store_diagnosis_snapshot`。
    2.  **统计节点**：利用 Python 沙箱/数据统计模块过滤出异常门店（如上海浦东店）。
    3.  **内搜节点**：检索企业知识库（`kb_search`）中的整改方针与条款。
    4.  **填表节点**：根据模板将异常门店名称、销售、客流及对应的整改建议填入行。
    5.  **导出节点**：调用 `xlsx` 渲染服务，生成并输出 Excel 文件。

### 用例 4.3：海外供应链单据处理与入账归档 (Global Supply Chain Billing & Auto-Filing)
*   **涉及节点**：`材料` $\rightarrow$ `抽取` $\rightarrow$ `翻译` $\rightarrow$ `工具` $\rightarrow$ `生成`
*   **业务场景**：海外供应商发来外文发票 PDF，系统读取材料，抽取金额税率，翻译清单，并调用 ERP 入账 API 记录。
*   **测试 Prompt (显式步骤版)**：
    > “请读取我上传的英文商业发票 PDF，抽取发票号、日期、买卖双方以及商品明细清单。将商品明细清单翻译成中文后，调用系统中的发票自动登记工具，把发票号、开票金额和翻译后的明细数据登记到 ERP 中，并输出一份入账登记确认书。”
*   **测试 Prompt (业务视角版 - 推荐)**：
    > “刚收到海外供应商发来的这封英文账单 PDF（已上传），请帮我提取出里面的发票号、金额和详细商品清单，翻译成中文，然后帮我自动录入到我们的 ERP系统里报销入账。完成后给我出一份入账成功的凭证说明。”
*   **预期图规划**：
    1.  **材料节点**：加载并解析上传的商业发票 PDF。
    2.  **抽取节点**：从 PDF 文本中提取关键的结构化元数据（发票号、开票额等）。
    3.  **翻译节点**：将发票中的英文清单翻译成中文。
    4.  **工具节点**：调用 ERP 系统中的登记 API 将数据归档。
    5.  **生成节点**：生成包含 ERP 系统流水号和录入结果的入账登记确认书。
